# 新功能开发流程

每个新功能（或新项目）在写第一行代码之前，按这个顺序走一遍。目的是**把「我觉得应该这样」换成「我验过，所以这样」**，并且在三个月后还能说清楚当初为什么这么选。

这份流程不是给简历看的，是给「一个人做项目、没人 review、容易一头扎进实现」的情况设计的。核心只有两条：

1. **先证明问题是真的，再证明方案是对的。**
2. **每一步都要留下可以被推翻的书面结论。**

---

## 0. 一句话定义（10 分钟）

用一句话写清楚，缺一个就说明还没想明白：

> 让**谁**，在**什么场景**下，能做**什么以前做不到的事**；不做会怎样。

对照检查：

- 是「用户的问题」还是「我的技术兴趣」？后者也能做，但要承认。
- 不做会怎样？如果答案是「也没什么影响」，就先别做。
- 这件事现有产品/现有代码真的做不到吗？还是只是做得不够顺？

**产出**：一段 2–3 行的话，写进 ADR 顶部。

**常见错误**：把方案写进定义（「用向量库做附件检索」是方案，不是问题）。

---

## 1. 现状盘点（30 分钟）

在看外部方案之前，先把自己有什么摸清楚。**大多数功能不是从零开始，是已有能力的重新组合。**

要盘的：

| 项 | 问什么 |
| --- | --- |
| 已有代码 | 仓库里哪些模块和这件事相关？函数签名是什么？ |
| 已有能力 | 模型/接口已经支持的能力（常被忽略，例如模型原生多模态） |
| 复用点 | 哪些能直接调、哪些要改、哪些不能用 |
| 真实缺口 | 扣掉能复用的，还剩多少活儿 |
| 现有约束 | 延迟、成本、鉴权、部署方式上的硬限制 |

**产出**：一张「能复用 / 要改 / 没有」三栏表。

**常见错误**：跳过这步直接搜「XXX 最佳实践」，结果方案里有 70% 是你已经有的东西。

---

## 2. 外部方案调研（1–2 小时）

至少找 **3 条** 路线，其中必须包含「什么都不做/最笨的办法」。只找到一条，说明搜得不够。

调研时只记事实，不记结论：

- 官方文档怎么写的（端点、限制、计费）
- 谁在生产环境用过（博客、issue、案例）
- 已知的坑（issue 里抱怨最多的那几条）

**产出**：每条路线 3–5 行，含出处链接。

**常见错误**：只看官网营销页。真正的坑在 issue 和定价页的脚注里。

---

## 3. 横向对比（固定维度）

维度固定下来，避免每次凭感觉选：

| 维度 | 说明 |
| --- | --- |
| 工作量 | 人日，含测试 |
| 延迟 | 用户能感知的等待（秒） |
| 单位成本 | 每次调用/每千次的实际花费 |
| 可逆性 | 选错了换回来要多久 |
| 厂商锁定 | 换供应商要改多少代码 |
| 可控性 | 出问题时能不能定位到具体环节 |
| 维护成本 | 三个月后还看得懂吗 |

**打分不要求精确，要求能比较。** 「工作量 3 人日 vs 0.5 人日」这种数量级对比比小数点重要。

**产出**：一张对比表 + 一句「我选 X，因为我最在乎 Y」。

---

## 4. 决策记录（ADR）

一个功能一个文件：`docs/adr/NNNN-功能名.md`（四位序号）。

模板：

```markdown
# NNNN. 功能名

日期：YYYY-MM-DD
状态：提议 / 已采纳 / 已废弃

## 背景
（第 0 步那段话 + 为什么现在做）

## 现状
（第 1 步的三栏表，只写结论）

## 备选方案
### A. xxx
- 做法：
- 优点：
- 缺点：
- 出处：

### B. ...

## 决策
选 X。因为（按优先级列 2–3 条理由）。

## 放弃了什么
（明确写出来。没有放弃的决策不是决策。）

## 分期
P0 … / P1 … / P2 …
```

**为什么要写**：三个月后你会忘记为什么没用那个「看起来更优雅」的方案，然后重新纠结一遍。ADR 就是给未来的自己留的备忘。

---

## 5. 最小切片（P0）

P0 的定义不是「先做简单的」，是**能独立验证核心假设的最小完整链路**。

判断标准：

- 用户能用它完成一次真实任务（不是「能跑」）
- 能独立上线/回滚，不依赖后面的阶段
- 一周内能做完

如果 P0 需要三周，说明还没切到位，继续切。

**反例**：「先做数据库表结构」不是 P0，那是内部的，验证不了任何用户价值。

---

## 6. 验收标准（写在做之前）

三条以内，可测：

- 功能：什么操作 → 什么结果
- 性能：延迟/成本上限
- 回归：现有测试全部通过 + 关键路径手工过一遍

**常见错误**：写「体验流畅」这种无法验收的话。

---

## 7. 落地与回归

- 先写测试再接前端（或至少同时）
- 改完跑 `pytest`，全绿才算完
- 涉及前端的，用无头浏览器截图核对，不靠脑补
- 更新 `docs/ARCHITECTURE.md` 里对应的设计说明（这仓库的文档是「为什么」，不是「怎么跑」）

---

## 8. 复盘（做完当天，10 分钟）

只回答两个问题，追加到 ADR 末尾：

1. 哪一步的假设错了？（下次同类功能能提前发现）
2. 哪里比预期慢？（是估算问题还是执行问题）

---

## 附：什么时候可以跳过这套流程

- 改文案、调样式、修 bug —— 直接做
- 一小时以内能做完且能立刻回滚的 —— 直接做
- 探索性的技术验证（spike）—— 可以只做第 1、2 步，结论口头说清即可

**但只要涉及**：新的外部依赖、数据模型变更、花钱的接口、用户可见的交互流程 —— 老老实实走完。
